# Website guide

This directory builds the site published at [openslo.com](https://openslo.com) with MkDocs Material, and
publishes it to the `gh-pages` branch from `main`. Object pages and their navigation are generated at
build time from `api.json`, which is imported from the OpenSLO Go SDK.

## Commands

Run these from the repository root:

| Command                | Purpose                                           |
| ---------------------- | ------------------------------------------------- |
| `make website/serve`   | Preview with live reload                          |
| `make website/build`   | Strict build into `website/site/`                 |
| `make website/check`   | Lints Python and runs the unit tests              |
| `make test`            | `python -m unittest discover -s website/tests`    |
| `make format`          | `ruff format website`                             |
| `make check/examples`  | Decodes and validates YAML examples from the docs |
| `make generate/schema` | Replaces `api.json` with an SDK manifest          |

The build runs with `--strict` and `macros.on_error_fail: true`, so a failing macro or an undefined
template variable fails it instead of rendering a warning.

## How a page is produced

1. `api.json` holds one entry per API version and object kind with property paths, documentation,
   allowed values, and validation rules. It is generated by the Go SDK and is never edited here.
2. `main.py` is the MkDocs hook. It registers the macros, creates a page for every version and object
   kind that is not already on disk, and rebuilds the `Schema` entry in the navigation.
3. `schema.py` is the engine: it parses and validates `api.json`, resolves `property-links.json`,
   derives anchors, and rewrites Go SDK symbol links to site pages.
4. `templates/*.j2` render the property panels, validation rule tables, and version overviews.

The macros available in Markdown are `generate_object_description`, `generate_object_properties`,
`generate_version_overview`, and `generate_version_links`.

## Authored versus generated

- Authored: `docs/index.md`, `docs/specification.md`, `docs/tools.md`, `docs/schema.md`,
  `docs/blog/`, `docs/schema/v1/{service,sli,slo}.md`, `docs/extra.css`, and `docs/property-details.js`.
- Generated during the build: every other `schema/<version>.md` and `schema/<version>/<kind>.md` page,
  plus everything under `site/`.
- Adding `docs/schema/<version>/<kind>.md` (lowercase kind, such as `alertcondition.md`) overrides
  generation and may add prose and examples around the macros.

## Editing guidance

- Specification prose and its examples: `docs/specification.md`.
- Object examples: add a `=== "Label"` tab block containing a complete object to the matching
  `docs/schema/v1/*.md` page. `make check/examples` decodes and validates every fenced YAML block that
  contains `apiVersion:` and no `name: string` placeholder.
- Shared property definitions and symbol links: `property-links.json`. Keep its structure: the version
  key is the raw API version such as `openslo/v1`, and each version holds `_types`, `_common`, kind
  names, and `_symbols`.
- Anchors: a property heading id is its path with `[*]` becoming `-items`, `.*` becoming `-values`,
  `.*~` becoming `-keys`, and the remaining dots becoming dashes. Fragments in `property-links.json`
  must match these ids, and the two rules must be changed together.
- Preserve the markup contract that `docs/extra.css` and `docs/property-details.js` depend on:
  `details.property`, `.property-controls`, `[data-property-action]`, `.property-type-badge`, and
  `.property-status-badge`.
- Templates render with `StrictUndefined` and may only use the variables the caller passes, so a new
  variable in a template needs a matching change in `schema.py`.
- Markdown lint rules are relaxed here: the line length rule is disabled and inline HTML and sibling
  duplicate headings are allowed. The remaining defaults in `.markdownlint.json` still apply.
- Blog posts live in `docs/blog/posts/` and need `title`, `slug`, `date`, `draft`, `authors`, and
  `categories`. Authors must exist in `docs/blog/.authors.yml`, and an existing `slug` is a published
  URL that a test asserts, so do not change one.

## Tests

`tests/test_schema.py` uses the standard library `unittest` and builds the site once per class.
`SchemaBuildTests` copies the project to a temporary directory, injects a synthetic `Probe` object into
the manifest, and asserts against the built HTML. Extend that synthetic object rather than the real
`api.json`, and assert on parsed content instead of raw HTML. Build failure cases belong in
`SchemaFailureTests`.

`tools/example-check` is a small Go module that validates complete YAML examples through the public Go
SDK decoder and validator. Its SDK revision in `go.mod` is pinned on purpose; update it only when the
examples must follow a different SDK revision.

See `README.md` in this directory for the schema import procedure and the full reference configuration.
